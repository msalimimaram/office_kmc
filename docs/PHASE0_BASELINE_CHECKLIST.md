## 1. هدف و مرز فاز صفر

هدف این فاز تثبیت یک baseline قابل استناد است: بدانیم دقیقاً کدام commit بررسی شده، چه ماژول‌ها و migrationهایی وجود دارند، کدام نیازمندی در کد دیده می‌شود، کدام تصمیم‌ها قطعی‌اند، چه چیزهایی ناقص یا نامعلوم‌اند و هر مورد در کدام فاز باید تکمیل شود.

در این فاز قابلیت محصولی جدید، migration، تغییر مدل، تغییر داده، seed یا refactor اجرایی انجام نمی‌شود. اصلاحات این فاز محدود به مستندات، ردیابی نیازمندی و رفع تناقض اسناد است.

## 2. قواعد حاکم

1. فقط شاخه `main`؛ شاخه جدید، PR و GitHub Actions ایجاد نشود.
2. هر بررسی به SHA دقیق و تاریخ وابسته باشد.
3. نتیجه ایستا با نتیجه runtime یکی نیست؛ وجود تست در سورس به معنی PASS نیست.
4. تست‌های قدیمی بدون SHA دقیق به HEAD فعلی منتسب نمی‌شوند.
5. هیچ migration، seed، پاک‌سازی یا reset روی دیتابیسی که باید حفظ شود انجام نشود.
6. خطای تست با حذف assertion، تضعیف مجوز یا bypass کردن Workflow gate حل نشود.
7. هر نیازمندی باید وضعیت و فاز مقصد داشته باشد.
8. درخواست بهبود ظاهری یا قابلیت خارج از معیار خروج به backlog منتقل شود؛ فاز جاری به‌خاطر «می‌شود بهترش کرد» باز نمی‌ماند.

## 6. معیار خروج رسمی فاز صفر

فاز صفر فقط وقتی CLOSED می‌شود که تمام موارد زیر برقرار باشند:

1. SHA و شاخه remote دقیق ثبت شده باشد.
2. وضعیت checkout محلی و اختلاف آن با remote مشخص باشد.
3. تمام اپ‌ها و migrationهای موجود inventory شده باشند.
4. تمام نیازمندی‌های کلیدی شناسه و وضعیت داشته باشند.
5. تناقض‌های نقش‌ها، seed، GitHub Actions و وضعیت تست تعیین تکلیف شده باشند.
6. هر نیازمندی یکی از وضعیت‌های STATIC_PRESENT / PARTIAL / NEEDS_DECISION / UNVERIFIED / OUT_OF_SCOPE داشته باشد.
7. backlog فازهای بعد و تصمیم‌های باز مالک ثبت شده باشند.
8. هیچ ادعای تست بدون SHA و خروجی واقعی ثبت نشده باشد.
9. گزارش baseline و ماتریس ردیابی در main ثبت و از نو خوانده شده باشند.

**نقطه پایان فاز صفر:** baseline remote قابل استناد + ماتریس ردیابی + تصمیم‌نامه + تأیید وضعیت checkout محلی. پس از آن فاز صفر بسته می‌شود؛ آزمون‌های runtime در فاز یک شروع می‌شوند.
