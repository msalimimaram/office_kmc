# معماری سامانه

## 1. نمای کلی

پروژه یک برنامه Django ماژولار با قالب‌های server-rendered است. `config` نقطه تنظیم و مسیریابی ریشه است؛ اپ‌ها مدل‌های دامنه، فرم‌ها، viewها، URLها و تست‌های مرتبط را نگه می‌دارند. `templates/` و `static/` رابط مشترک فارسی/RTL را فراهم می‌کنند.

## 2. مرز مسئولیت‌ها

- `accounts`: هویت، نقش سازمانی و وضعیت تغییر رمز.
- `organizations`: ساختار شرکت مادر/تابعه، کارکنان و وابستگان.
- `insurance`: بیمه‌گران، رشته‌های بیمه، قراردادها و اصلاحیه‌ها.
- `claims`: پرونده خسارت و مقادیر ثبت/ارزیابی/قابل‌پرداخت/پرداخت‌شده.
- `requests_portal`: درخواست‌های کاربران و وضعیت رسیدگی.
- `tasks`: وظایف داخلی و مسئولان.
- `documents`: متادیتا و فایل‌های اسناد.
- `imports`: batchهای ورود Excel و گزارش اعتبارسنجی.
- `auditlog`: مدل رویداد حسابرسی.
- `assets`: دارایی‌های بیمه‌شده.
- `announcements`: اطلاعیه و بخشنامه.
- `correspondence`: ثبت مکاتبه و پیگیری.
- `dashboard`: صفحه اصلی.
- `core`: کنترل‌های مشترک مانند مجوزها و اعتبارسنجی فایل.
- `config`: settings، URL root و WSGI/ASGI.

## 3. الگوی درخواست

1. درخواست به URLهای ریشه در `config/urls.py` می‌رسد.
2. middleware جنگو نشست و هویت را پردازش می‌کند؛ middleware تغییر رمز اجباری نیز در مسیر درخواست قرار دارد.
3. URL اپ view مربوطه را انتخاب می‌کند.
4. view باید احراز هویت، نقش و محدوده queryset را در سمت سرور بررسی کند.
5. فرم/model validation ورودی را اعتبارسنجی می‌کند و ORM داده را ذخیره/بازیابی می‌کند.
6. template پاسخ HTML فارسی/RTL را رندر می‌کند.

این توالی یک الگوی طراحی است؛ بازبین باید هر view را جداگانه برای رعایت همه مراحل بررسی کند.

## 4. مرز امنیت داده

نقش به‌تنهایی برای مجوزدهی کافی نیست. محدودیت‌های لازم ممکن است به شرکت کاربر، شناسه بیمه‌گر، رابطه فرد با کارمند، محرمانگی درخواست و انتساب پرونده وابسته باشد. مجوز باید در queryها و عملیات جزئیات/ویرایش/دانلود اعمال شود؛ ID غیرقابل‌حدس جایگزین مجوز نیست.

`core.permissions` فیلترهایی مانند `scoped_claims_for` و `scoped_requests_for` دارد. این helperها به‌تنهایی اثبات نمی‌کنند که تمام مسیرها از آن‌ها استفاده می‌کنند؛ audit کامل endpointها و Admin لازم است.

## 5. داده و فایل

- `DATABASE_URL` برای PostgreSQL در محیط غیرتوسعه‌ای استفاده می‌شود؛ SQLite فقط برای توسعه محلی.
- فایل‌های کاربر در `private_media` قرار می‌گیرند؛ تنظیم مسیر فایل به‌تنهایی تضمین نمی‌کند که وب‌سرور آن‌ها را خصوصی ارائه دهد.
- فایل Excel باید اعتبارسنجی شود و ورود گروهی باید قابل بازبینی باشد.
- مبالغ خسارت از تراکنش بانکی مستقل‌اند و سامانه درگاه پرداخت نیست.

## 6. نقاط فنی مهم

- مدل کاربر سفارشی `accounts.User` است؛ باید پیش از اولین migration عملیاتی تثبیت شود.
- migrationها باید در Git نسخه‌بندی شوند و روی یک پایگاه داده خالی و یک نسخه دارای داده آزمایش شوند.
- تغییرات مدل، مجوز یا upload باید تست رگرسیون داشته باشند.
- کارهای حجیم و زمان‌بر در نسخه فعلی لزوماً صف پس‌زمینه ندارند.
- رابط CSS واکنش‌گراست، اما بررسی واقعی در دستگاه/مرورگر هنوز بخشی از پذیرش محصول است.

## 7. دیاگرام متنی

```text
Browser
  -> Django middleware (session, auth, password-change gate)
  -> config/urls.py
  -> app urls.py / views.py
  -> server-side permissions + scoped QuerySet
  -> forms / models / ORM
  -> PostgreSQL (production) or SQLite (local development)
  -> templates/ + static/css/site.css
```
