# راهنمای آزمون محلی و پذیرش

این پروژه عمداً GitHub Actions ندارد. اجرای تست‌ها در این مرحله از روی سیستم توسعه‌دهنده انجام می‌شود.

## 1. آماده‌سازی محیط محلی Windows

از Python 3.11 یا 3.12 استفاده کنید. فایل .env.local.example برای اجرای سریع با SQLite آماده است و Docker لازم نیست.

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
Copy-Item .env.local.example .env -Force
```

اگر PowerShell اجرای اسکریپت فعال‌سازی را مسدود کرد، فقط برای پنجره فعلی اجرا کنید:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1
```

## 2. بررسی کد و migrationها

ابتدا دستورهای بدون تغییر پایگاه داده را اجرا کنید:

```powershell
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py migrate --plan
python manage.py showmigrations
```

انتظار: check بدون خطای سیستمی تمام شود؛ makemigrations اعلام کند تغییر مدل بدون migration وجود ندارد؛ migrate --plan برنامه مهاجرت‌ها را نشان دهد. اگر هرکدام خطا داد، خروجی کامل را نگه دارید و قبل از ادامه گزارش کنید.

سپس روی دیتابیس محلی خالی:

```powershell
python manage.py migrate
python manage.py showmigrations
```

تمام migrationهای برنامه باید علامت [X] داشته باشند.

## 3. اجرای تست‌های خودکار

```powershell
python manage.py test
```

برای اجرای گروهی تست‌های مهم:

```powershell
python manage.py test accounts organizations claims requests_portal imports workflow correspondence assets documents tasks
```

در صورت شکست، خروجی کامل اولین خطا و traceback را ذخیره کنید. تا رفع خطاهای تست و migration، شاخه را در main ادغام نکنید.

## 4. ساخت داده ساختگی و اجرای سایت

```powershell
python manage.py seed_demo
python manage.py seed_operational_workflows
python manage.py audit_workflows
python manage.py runserver
```

سپس نشانی http://127.0.0.1:8000/ را باز کنید.

رمز مشترک حساب‌های نمونه فقط در محیط توسعه: **DemoPass!2026**

| حساب | نقش | هدف آزمون |
|---|---|---|
| admin.demo | مدیر سامانه | تنظیمات و دسترسی سراسری |
| head.demo | رئیس اداره | مشاهده سراسری و نظارت |
| specialist.demo | کارشناس درمان | دسترسی تخصصی رشته درمان |
| companya.demo | نماینده شرکت الف | محدوده شرکت الف |
| companyb.demo | نماینده شرکت ب | محدوده شرکت ب |
| employee.a | بیمه‌شده شرکت الف | مشاهده و ثبت درخواست شخصی |
| employee.b | بیمه‌شده شرکت ب | جداسازی سوابق شرکت ب |
| insurer.demo | نماینده بیمه‌گر نمونه | ورود اطلاعات و دامنه بیمه‌گر |

این حساب‌ها فقط داده ساختگی دارند. برای آزمون پنل Django Admin با تمام مجوزهای پیش‌فرض، یک superuser جداگانه با دستور createsuperuser بسازید.

## 5. سناریوهای دستی پذیرش

1. با companya.demo وارد شوید و بررسی کنید داده‌های شرکت ب قابل مشاهده یا جست‌وجو نباشند.
2. با companyb.demo وارد شوید و همین آزمون را برای شرکت الف انجام دهید.
3. با employee.a وارد شوید و بررسی کنید سوابق و درخواست‌های کارمند دیگر نمایش داده نشود.
4. با specialist.demo دسترسی درمان را بررسی کنید؛ رشته‌های فاقد انتصاب نباید قابل دسترسی باشند.
5. با insurer.demo بررسی کنید اطلاعات بیمه‌گر دیگر قابل مشاهده یا ثبت نباشد.
6. با نماینده شرکت جدید، سوابق مجاز کارمند منتقل‌شده را بررسی کنید و با نماینده شرکت قبلی، محدوده شرکت سابق را بسنجید.
7. درخواست محرمانه درمان را ایجاد/مشاهده کنید و دسترسی نماینده شرکت و کارشناس عادی را با دسترسی رئیس اداره مقایسه کنید.
8. در ورود Excel، فایل نامعتبر، تاریخ نامعتبر، مبلغ منفی و فایل دارای ستون اجباری ناقص را امتحان کنید.
9. در گردش کار، مشاهده، تأیید مشاهده، ارجاع با توضیح اجباری و اقدام غیرمجاز را بررسی کنید.
10. در پرداخت، ثبت قسط، تأیید مستقل و برگشت پرداخت را با داده ساختگی بررسی کنید.
11. با کارشناس رشته قرارداد جدید ثبت کنید؛ باید پیش‌نویس و نسخه pending ساخته شود و فقط رئیس اداره/مدیر سامانه بتواند WorkflowCase را نهایی ببندد.
12. یک اصلاحیه با تاریخ اثر آینده ثبت کنید؛ قبل از تاریخ اثر نسخه جاری نباید تغییر کند؛ پس از اجرای apply_due_contract_revisions باید snapshot جدید اعمال شود.
13. درخواست فسخ را با خسارت باز ثبت کنید؛ پیش‌نمایش خسارت‌ها را ببینید، تأیید نهایی را با رئیس اداره انجام دهید و مطمئن شوید خسارت باز بسته نمی‌شود.
14. با نماینده شرکت/بیمه‌گر بررسی کنید پیش‌نویس‌ها و نسخه‌های pending دیده نشوند و سند قرارداد فقط از مسیر دانلود مجاز دریافت شود.
15. درخواست اصلاح موبایل/شبا/کد ملی را برای شخص اصلی و وابسته ثبت کنید؛ فقط مسیر نماینده شرکت → بیمه‌گر → نماینده شرکت باید اجرا شود.
16. پیش از بستن نهایی درخواست، مقدار Person و User نباید تغییر کند؛ پس از تأیید نهایی، هر دو باید در یک تراکنش به‌روزرسانی شوند.
17. درخواست ردشده نباید داده شخص را تغییر دهد؛ نماینده بیمه‌گر نباید بتواند درخواست متقاضی را ببندد.
18. نماینده غیرمسئول همان شرکت باید مقدار موبایل/شبا/کد ملی را ماسک‌شده ببیند؛ متقاضی و مسئول فعلی مقدار کامل را ببینند.
19. درخواست‌کننده‌ای که هم‌زمان تنها نماینده شرکت است باید بتواند درخواست خودش را به همان حساب ارجاع دهد؛ حساب نباید به دلیل exclude شدن خودکار بدون گیرنده بماند.

## 6. آزمون PostgreSQL (پیشنهادی پیش از پذیرش نهایی)

SQLite برای smoke test محلی است. شماره‌گذاری هم‌زمان مکاتبات، قفل ردیف‌ها و برخی constraintها باید روی PostgreSQL هم بررسی شوند.

```powershell
docker compose -f docker-compose.local.yml up -d db
```

در فایل .env خط DATABASE_URL را فعال کنید:

```text
DATABASE_URL=postgresql://office_kmc:office_kmc@127.0.0.1:5432/office_kmc
```

سپس یک پایگاه داده تمیز بسازید و مراحل بخش 2 و 3 را دوباره اجرا کنید. بعد از اتمام:

```powershell
docker compose -f docker-compose.local.yml down
```

## 7. اجرای یک‌جای دروازهٔ پیش‌انتشار در Windows

برای اجرای متمرکز کنترل وابستگی‌ها، Django check، نبود migration جاافتاده، کل تست‌ها و ممیزی پیکربندی گردش‌کار:

```powershell
.\scripts\final_preflight.ps1
```

فرمان `seed_operational_workflows` گردش‌کار نسخه‌دار پایه را برای تمام انواع ServiceRequest و فرآیندهای claim_objection، contract_approval، contract_termination، person_change و دارایی ایجاد می‌کند؛ تعریف‌های فعال موجود را بازنویسی نمی‌کند. سپس `audit_workflows` یک gate واقعی است و پوشش وضعیت‌ها، نقش‌ها، گیرنده‌ها و مسیرهای نهایی را کنترل می‌کند. اجرای seed به وجود انتصاب فعال رئیس اداره یا مدیر سامانه نیاز دارد. تصمیم نهایی اعتراض و قرارداد باید فقط در اختیار رئیس اداره/مدیر سامانه باشد. این شکست را با حذف gate یا خاموش‌کردن بررسی دور نزنید؛ ابتدا پیکربندی گردش‌کار و انتصاب گیرنده‌ها را تکمیل کنید.

برای کنترل تنظیمات Production، فقط روی staging با نسخهٔ پشتیبان/کپی پایگاه داده اجرا کنید:

```powershell
.\scripts\final_preflight.ps1 -Production
```

حالت `-Production` تست‌ها را نیز اجرا می‌کند؛ هرگز آن را با `DATABASE_URL` پایگاه دادهٔ زندهٔ Production اجرا نکنید. این اسکریپت schema را migrate نمی‌کند؛ فقط وضعیت migration را بررسی می‌کند و static files را جمع‌آوری می‌کند.

## 8. آزمون اسکن بدافزار فایل‌ها

در محیط توسعه با `DEBUG=True` نبودن ClamAV مانع تست‌های ساختاری فایل نمی‌شود. در Production، `CLAMD_HOST` اجباری است و سرویس باید از شبکه خصوصی برنامه قابل دسترسی باشد. پیش از پذیرش، در staging این سناریوها را اجرا کنید:

- فایل PDF/Office سالم با پاسخ `stream: OK` پذیرفته شود.
- فایل آزمایشی استاندارد EICAR شناسایی و پیش از ذخیره رد شود.
- در صورت توقف ClamAV یا timeout، upload رد شود و هیچ رکورد/فایل ناقصی باقی نماند.
- فایل Excel واردشده نیز قبل از parse و ذخیره batch اسکن شود.

## 10. تفویض اختیار و صندوق گیرنده

پس از `migrate`، فرمان `python manage.py verify_database_schema` وجود جدول‌های اطلاعیه و مکاتبات را بررسی می‌کند. برای پذیرش تفویض:

1. با رئیس اداره یا مدیر سامانه از «مدیریت تفویض اختیار» یک تفویض با گردش‌کار، زیرنوع، رشته/شرکت، گیرنده، دلیل و تاریخ اعتبار ثبت کنید.
2. پرونده‌های باز در مرحله آغازین و پرونده‌های جدید مطابق محدوده تفویض به گیرنده منتقل می‌شوند.
3. با حساب گیرنده وارد شوید؛ خلاصه کارها در داشبورد و فهرست کامل در «کارهای تفویض‌شده» باید دیده شوند.
4. پس از ارجاع به مسئول مرحله بعد، پرونده از صندوق تفویض گیرنده خارج می‌شود.
5. تعلیق، لغو، پایان اعتبار یا از دست رفتن انتصاب باید پرونده‌های باز را به تفویض‌کننده بازگرداند.
6. سناریوی ویژه: `person_change` + `iban` + `insurance_specialist` + رشته `health`. انواع دیگر اصلاح اطلاعات نباید با این قاعده منتقل شوند.

تست باید با دو شرکت مستقل و با بررسی جلوگیری از بستن نهایی توسط کارشناس تفویض‌شده و جلوگیری از مشاهده پرونده خارج از محدوده انجام شود.
